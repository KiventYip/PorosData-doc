# PorosData-Processor

## 定位

`Processor` 是 PorosData 中负责质量整理的模块。它的任务不是生成最终结构化结果，而是把上游解析输出整理成稳定、清晰、可继续处理的中间数据，为后续结构化和批量利用打好基础。

简而言之：

- `Processor` 解决“原始内容是否足够干净、稳定、可继续使用”
- `Designer` 解决“这些内容如何组织成最终交付结果”
{: .tight-list}

## 适合处理什么问题

`Processor` 主要面向以下典型问题：
{: .section-intro}

- OCR 造成的异常空格、断词和断裂数字
- 材料名、术语、单位和化学式的误写或碎裂
- 图注、表题、脚注中的噪音和格式残留
- 引文、公式和上下文锚点在解析后变得不稳定
{: .tight-list}

## 输入与输出

### 输入内容

`Processor` 通常接收来自上游解析阶段的原始结果，例如：
{: .section-intro}

- 正文文本块
- 图注与表题
- 图片相关元数据
- `*_content_list.json` 一类内容列表文件
{: .tight-list}

### 输出内容

标准输出通常写入 `data/processed/`，包括：
{: .section-intro}

- 清洗后的内容列表
- 可复用的图片资源副本
- 批处理报告，如 `processing_report.json`
- 面向复核的质量检查结果与异常模式线索
{: .tight-list}

这一步的结果仍然属于中间层，不直接承担最终交付展示，但会直接决定后续结构化结果的稳定性。

## 用户能获得什么

使用 `Processor` 后，用户通常会得到以下改进：
{: .section-intro}

- 数字、单位和公式边界更清晰
- 术语与材料名称更稳定
- 图注、表题和脚注更适合后续抽取
- 文本更适合训练、检索和规则处理
{: .tight-list}

## 处理范围

`Processor` 不只处理正文，也覆盖关键元数据字段，例如：
{: .section-intro}

- `text`
- `image_caption`
- `image_footnote`
- `table_caption`
- `table_footnote`
{: .tight-list}

这样做的目的是保证正文与图表信息在进入下游之前保持同一质量标准。

## 典型清理内容

| 类型 | 常见问题 | 目标结果 |
|------|------|------|
| 数值修复 | `0 . 0 1 0 n m` | `0.010nm` |
| 元素修复 | `N i` | `Ni` |
| 行内碎裂修复 | `110 \\n s` | `110s` |
| 术语统一 | `Zr based` / `Zr-based` | 同文档内尽量统一 |
| 引文整理 | `[2,3]`, `[1-3]` | 统一为稳定协议 |

## 运行与部署建议

### 推荐环境

- Linux 服务器优先
- Python `3.8+`
- 常规批量建议使用 SSD 或 NVMe
- 不需要 GPU
{: .tight-list}

### 参考配置

| 场景 | 建议配置 |
|------|------|
| 小规模验证 | 4 vCPU / 16 GB RAM |
| 常规批处理 | 8 vCPU / 32 GB RAM |
| 长时大批量运行 | 16 vCPU / 64 GB RAM |

### 推荐使用方式

- 日常批量清洗优先关注稳定性
- 评估类附加功能建议在抽检或审计阶段单独开启
- 长文档较多时，适当降低并行度通常更稳妥
{: .tight-list}

## 运行时表现

`Processor` 是典型的 CPU 密集型流程。整体耗时通常受到以下因素影响：
{: .section-intro}

- 文档长度和公式复杂度
- 并行 worker 数量
- 是否开启额外评估统计
- 当前运行环境是 Windows 还是 Linux
{: .tight-list}

如果日志持续推进、处理报告不断更新，通常说明任务在正常运行，而不一定是卡住。

## 质量复核机制

对于对外交付项目，`Processor` 不只负责清洗，还应支持持续复核。推荐将这一阶段理解为一个逐步收敛的质量闭环：
{: .section-intro}

1. 完成批量处理，形成标准中间结果
2. 对结果进行质量检查，识别可疑模式和残留问题
3. 对高频问题补充修正策略
4. 重新处理并再次复核，直到结果达到可交付状态
{: .tight-list}

这种机制更适合外部项目中的稳定交付，也有助于持续减少重复性噪音问题。

## 已知边界

使用 `Processor` 时需要注意：
{: .section-intro}

- 它不负责最终目录建模或知识组织
- 它不会替代人工定义业务字段
- 对结构极其复杂的公式和版式，优先保证不破坏原始结构，而不是激进改写
{: .tight-list}

## 与 `Designer` 的关系

`Processor` 的输出越稳定，`Designer` 的结构化结果越可靠。推荐把它视为交付链路中的质量入口，而不是最终结果本身。
