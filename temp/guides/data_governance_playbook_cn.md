# 数据治理操作手册

*最后更新：2026-03-19*

[English Version](data_governance_playbook.md)

本手册描述了如何使用 `porosdata_processor` 的审计和规则工作流来实现持续的、数据驱动的质量改进。面向需要理解流程、做出判断决策并跟踪进度的操作人员。

## 核心原则

> 质量改进通过添加声明式 TOML 规则实现——不修改 Python 代码。
>
> 每次改进循环必须可追溯：带时间戳的产物、可审计的结果、清晰的决策轨迹。

---

## 数据治理闭环

```
┌───────────────────────────────────────────────────────────────┐
│                                                               │
│  ┌─────────┐    ┌──────────────┐    ┌──────────────────────┐  │
│  │  审计    │───>│  识别差距    │───>│  引导候选规则        │  │
│  └─────────┘    └──────────────┘    └──────────────────────┘  │
│       ^                                        │              │
│       │                                        v              │
│  ┌─────────────┐  ┌────────────┐   ┌──────────────────────┐  │
│  │  交付门禁   │<──│  推广规则  │<──│  样本验证            │  │
│  └─────────────┘  └────────────┘   └──────────────────────┘  │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

每一步都产生产物供下一步使用。闭环永不停止——每次交付后会触发新的审计循环。

## 逐步操作流程

### 第一步：审计（Audit）

**目的**：发现已处理数据中的质量问题。

**命令**：
```bash
python run_processor.py audit
```

**执行内容**：
- 使用 `detect_audit.toml` 中的模式（OCR 残留、质量模式）检测处理后的数据。
- 执行 Python 结构化检查（美元符号配对、引用指标、元数据覆盖率）。
- 生成 JSON 报告：`docs/audit/aiready_data_audit_result.json`。

**需要人工判断**：
- 审查标记的问题，判断是真正的问题还是误报。
- 按严重程度排列优先级（阻塞级 vs. 警告级）。
- 决定哪些问题需要新规则、哪些是可接受的边缘情况。

**产出**：带时间戳的审计结果（`aiready_data_audit_result.json`，包含 ISO 时间戳字段）。

---

### 第二步：识别差距（Identify Gap）

**目的**：分类每个审计发现并决定响应方式。

**决策矩阵**：

| 发现类型 | 响应方式 | 位置 |
|---|---|---|
| 正则可修复的模式 | 添加 TOML 规则 | 规范规则包 |
| 结构性/算法性问题 | 代码修复（需批准） | Python 源码 |
| 检测中的误报 | 优化审计模式 | `detect_audit.toml` |
| 可接受的边缘情况 | 记录并跳过 | 审计备注 |

**需要人工判断**：
- 检查被标记文本的上下文，理解模式实际匹配到了什么。
- 使用 `scripts/check_hyphen_context.py` 等临时脚本详细检查匹配项。
- 判断规则能否安全地修复问题而不引入回归。

---

### 第三步：引导候选（Bootstrap Candidate）

**目的**：为识别的差距创建候选规则。

**命令**：
```bash
python run_processor.py bootstrap-candidate
```

**执行内容**：
- 根据审计发现生成候选规则条目。
- 候选规则放置在暂存区，待审查后再推广。

**规则编写规范**：
- 规则 ID 格式：`{domain}.{target}.{description}`（如 `post_shield.unwrap.element_based`）。
- 每条规则必须包含：`id`、`priority`、`target`、`pattern`、`replacement`。
- 在继续之前，用实际标记的文本测试正则表达式模式。

---

### 第四步：样本验证（Sample Validate）

**目的**：验证候选规则是否正确工作且不会导致回归。

**命令**：
```bash
python run_processor.py sample-validate
```

**执行内容**：
- 将候选规则应用到样本数据上。
- 检查替换链冲突（一条规则的输出意外触发另一条规则）。
- 报告匹配计数和任何意外副作用。

**需要人工判断**：
- 审查验证输出中的意外匹配。
- 检查替换结果在语义上是否正确，而不仅仅是语法有效。
- 验证规则不会过度匹配（过宽）或匹配不足（过窄）。

---

### 第五步：推广规则（Promote Rule）

**目的**：将验证通过的候选规则合并到规范规则包中。

**命令**：
```bash
python run_processor.py promote-rule
```

**执行内容**：
- 备份当前规范规则包，带 `YYYYMMDD_HHMMSS` 时间戳。
- 将验证通过的候选规则合并到规范包。
- 更新规则元数据。

**推广后操作**：
- 使用更新后的规则重新处理受影响的数据。
- 运行 `python -m pytest tests/unit/ -q` 验证无测试回归。

---

### 第六步：交付门禁（Delivery Gate）

**目的**：确认处理后的数据满足交付标准，零阻塞问题。

**命令**：
```bash
python run_processor.py delivery-gate
```

**执行内容**：
- 对所有已处理数据运行 `detect_delivery.toml` 阻塞检查。
- 按文档报告通过/失败状态。
- 任何一个阻塞问题都会导致整个门禁失败。

**需要人工判断**：
- 审查所有失败项，决定是创建额外规则还是申请例外。
- 门禁通过后签署交付确认。

## 时间戳和可追溯性要求

| 产物 | 时间戳格式 | 位置 |
|------|-----------|------|
| 审计 JSON 结果 | ISO 日期时间（自动设置） | `docs/audit/` |
| 审计报告文件 | 文件名中包含 `_YYYYMMDD` | `docs/audit/` |
| 规则备份 | 文件名中包含 `YYYYMMDD_HHMMSS` | `docs/rules/backups/` |
| CHANGELOG 条目 | 按日期分组 | `CHANGELOG.md` |
| 架构决策 | 账本条目中标注日期 | `ARCHITECTURE_LEDGER.md` |

## 常见场景

### 场景 A：处理后数据中发现 OCR 残留

1. 运行 `audit` — 查看 `ocr_pattern` 匹配项。
2. 使用临时脚本检查每个匹配的上下文。
3. 分类：属于 `repair_ocr.toml` 还是 `post_shield.toml` 的修复范围？
4. 向相应的规范包添加候选规则。
5. `sample-validate` → `promote-rule` → 重新处理 → `audit` → `delivery-gate`。

### 场景 B：公式格式问题

1. 运行 `audit` — 查看 `formula_hyphen_spacing` 等质量模式。
2. 检查：数学模式是否语义上必要？还是仅包裹了一个纯元素符号？
3. 如果是纯元素符号：向 `post_shield.toml` 添加 `unwrap` 规则。
4. 如果是语义上必要的公式：标记为误报，必要时优化审计模式。
5. 完成治理闭环。

### 场景 C：需要新的术语规范化

1. 在处理输出中识别不一致的术语。
2. 向 `normalize_terms.toml` 添加映射规则。
3. 验证、推广、重新处理、审计、门禁。

## 架构边界

决定修复位置时，遵守以下边界：

- **TOML 规则**：基于正则的模式匹配、文本替换、规范化映射。
- **Python 代码**：上下文感知逻辑、多步算法、有状态转换。
- **冻结元素**：pipeline 步骤序列、Shield 机制、模块层次——未经明确批准不得修改。
- **可扩展元素**：TOML 规则文件、检测模式、测试、文档。

详细的架构冻结边界请参阅项目 Skill 参考文档。
